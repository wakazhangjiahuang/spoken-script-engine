# 用户利益翻译｜Audience Value Translation

本文件用于把专业能力、技术功能、产品卖点和业务流程翻译成目标用户能理解的实际价值。不是夸大承诺，也不是把所有功能都写成“降本增效”。

## 核心表达链

`目标人群 → 具体场景 → 当前问题 → 影响/代价 → 解决机制 → 用户可获得的结果 → 证据 → 适用条件/边界`

每次只保留与本条视频主问题直接相关的链路。

## 六个必答问题

1. **关用户什么事？** 说清楚他正在做什么、卡在哪里。
2. **为什么现在值得听？** 说明问题造成的时间、成本、风险、决策困难或体验影响；没有数据时不要量化。
3. **到底改变了什么？** 说明实际流程、能力或决策方式，而不是堆产品功能名。
4. **用户能得到什么？** 用可观察、可理解的结果表达，避免“赋能、闭环、智能化”等空词。
5. **凭什么相信？** 用真实过程、原始材料、可复查数据、演示或有范围的案例支撑。
6. **什么情况下不适用？** 明确输入条件、权限、人工复核、成本和责任边界。

## 功能转利益表达

| 层级 | 需要回答 | 示例 |
|---|---|---|
| 功能 | 系统/产品能做什么 | 自动识别表格字段 |
| 机制 | 它如何工作 | 按预设字段规则提取并归类 |
| 场景 | 用户什么时候需要 | 每天整理多份格式相近的报价单 |
| 结果 | 用户得到什么 | 减少重复录入，便于统一核对 |
| 证据 | 如何证明 | 展示原始文件、运行过程和输出对照 |
| 边界 | 何时需要人工 | 异常字段、缺失资料和关键金额仍需复核 |

## 口播语言规则

- 先用用户熟悉的场景，再引入专业术语。
- 一句话只表达一个主要意思。
- 把抽象词换成动作、对象和结果。
- 不把“可能改善”写成“保证实现”。
- 不把计划演示写成已经完成的实测。
- 不把示例场景冒充真实客户案例。
- 不把模型生成的内容当成独立证据。

## 交付前检查

- 听众能否复述这条视频解决什么问题？
- 能否指出用户实际会得到什么？
- 结果是否有证据支撑？
- 条件和限制是否说清楚？
- 是否只讲了一个核心问题？
